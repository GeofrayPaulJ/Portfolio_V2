# MICCAI Educational Challenge 2026: Your GPU Is Lying To You

**MICCAI 2026** · **Tutorial on silent failures in challenge submissions** · `Education` `Verification` `MLOps`

---

## Result

- **Status: finalist.** MICCAI Educational Challenge 2026, MICCAI 2026, Strasbourg, France.
- Submission title: "Your GPU Is Lying To You". Subtitle: "And so is your test harness, your docstring, your validation set, and your cross-validation."

## The finding

Six instruments reported success while being wrong, and almost none of them needed real data to catch.

| Instrument | What was actually happening |
|---|---|
| The GPU | `torch.cuda.is_available()` returned True while every kernel launch failed, with a silent fallback to CPU. |
| Local timings | 175 to 433 s per case, measured on the CPU fallback, against about 35 s on the target GPU. 433 s exceeds the 420 s limit. |
| The test harness | Four `FileNotFoundError` tracebacks, while the container was correct on all four cases. |
| A docstring | It promised an all-background mask on any exception, but the read that could raise sat above the `try`. |
| The validation set | A file named for 100 cases held 103 images and 102 labels, one degenerate and one with an impossible label. |
| Cross-validation | +0.014 Dice (95% CI +0.009 to +0.019) became +0.0010 on test, and the target metric moved the wrong way. |

## Approach

The tutorial is built from the container work for [AIMS-TBI 2026](/challenges/aims-tbi-2026) in June and July 2026. I set out to write about Docker, but the Dockerfile was written once and never edited. The time had gone into measurement.

For each instrument, the tutorial shows the evidence, explains the mechanism and states a rule:

- Probe the GPU with a real kernel launch, not `torch.cuda.is_available()`, and print the selected device. A timing from a fallback path is not a measurement.
- Hexdump the output artefact before parsing it. The bytes above the traceback showed valid output; the harness was checking a stale hardcoded path.
- Put the input read inside the `try`, and run a deliberately corrupted input through every container. Two containers sharing an image and weights behaved differently on the same fixture.
- Audit the dataset before the first metric: file counts, image-to-label correspondence, intensity ranges, unique label values.
- Before spending a submission on a cross-validation gain, check which cases produced it. Mirroring sharpened predictions on lesions already found and did nothing for cases with the prediction in the wrong place, which dominate surface-distance metrics.

The tutorial includes a ten-point preflight checklist. It ships synthetic data, so it runs without weights, a GPU or a data agreement. The device probe needs no data, the corrupt-input test needs a truncated file, and the label audit needs a label array.

## Limitations

- The evidence is one submission's history on one platform. It shows that these failures occur, not how often.
- The checklist catches the failure classes it names. It does not replace a run on the real target platform, and synthetic fixtures say nothing about model quality.
- The work was never committed to version control, so the history was reconstructed from build logs, run logs and dated notes. Some records did not survive; the tutorial marks those gaps rather than filling them.
